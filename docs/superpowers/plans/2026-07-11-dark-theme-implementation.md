# Dark Theme Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a switchable light/dark theme to the Toph Hugo theme, defaulting to system preference, configurable per-site via `color_mode` (`auto`/`light`/`dark`) and symmetric `colors.light.*`/`colors.dark.*` config, wired up for both `exampleSite` and jwheel.org.

**Architecture:** CSS custom properties in two `:root` blocks (base + `[data-bs-theme="dark"]` override), generated by `head.html` from `data/style.yaml` (theme neutrals) and site config (brand colors). A blocking inline script sets `data-bs-theme` from `localStorage`/`prefers-color-scheme` before first paint; a navbar toggle flips it at runtime. `color-mix()` derives text-safe tints of brand colors live in the browser — no per-site color math in Hugo templates.

**Tech Stack:** Hugo `css.Build` vars (existing mechanism), vanilla JS (no build pipeline — matches existing theme convention), Bootstrap 5.3.8's native `data-bs-theme` support (already loaded via CDN, currently unused).

**Reference:** Design spec at `docs/superpowers/specs/2026-07-05-dark-theme-design.md`. GitHub issue: toph-hugo-theme#56.

## Global Constraints

- Hugo Extended ≥0.161.1 (existing floor; unchanged by this work).
- Every new/changed color must meet WCAG contrast against its actual rendering context: 4.5:1 for text, 3:1 for large text/UI components/non-text — verified by the relative-luminance formula, not eyeballed. All values in this plan are pre-verified (see per-task tables); do not substitute different values without re-verifying.
- No new runtime dependencies. Vanilla JS only, inline in partials — the theme has no JS build pipeline (`js.Build` is not used anywhere), so new script content goes inline in the relevant `.html` partial, matching the existing tweet-archive carousel script's convention.
- All color values as CSS custom properties, never hardcoded outside `data/style.yaml` and site `config.yaml` (existing rule, `AGENTS.md` #4 in the theme repo).
- **Git commits: never run `git commit`/`git push` directly.** At the end of each task, write the commit message to `/tmp/commit-<descriptive-name>.txt` and present the copy-pasteable command `git add <files> && git commit --edit --file=/tmp/commit-<name>.txt --gpg-sign --signoff` for the user to run themselves. This overrides this skill's default "Step 5: Commit" pattern — it is a hard project rule, not a preference.
- Commit subject format: `<gitmoji> <component>: <summary>`. Body is 3-6 sentences focused on WHY, not what/how. Trailer: `Assisted-by: Claude Sonnet 5 (1M context)`.
- Theme work happens in `themes/toph/` (a separate git repo, submodule of `jwheel.org`). Use `git -C themes/toph/ ...` when running theme-repo git commands from the `jwheel.org` root; commands presented to the user assume their cwd is `themes/toph/`.

## Task 1: Restructure `data/style.yaml` and `head.html` light-mode vars; migrate both configs to `colors.light.*`

This is the foundational schema migration. It must land as one task because splitting it would leave the Hugo build broken mid-way: once `style.yaml` nests its groups under `light:`/`dark:`, `head.html`'s current flattening loop (which assumes each group's entries are scalars, not sub-dicts) would iterate the wrong shape and produce garbage CSS values. This task changes the schema but not the values — light mode must look pixel-identical to production before and after.

**Files:**
- Modify: `themes/toph/data/style.yaml`
- Modify: `themes/toph/layouts/partials/head.html`
- Modify: `jwheel.org/config.yaml` (repo root, not the theme)
- Modify: `themes/toph/exampleSite/config.yaml`

**Interfaces:**
- Produces: CSS custom properties `--background`, `--primary-text`, `--accent-text` (new, passthrough to `--primary`/`--accent-color` in light mode) — Task 2 depends on these existing.
- Produces: `hugo.Data.style.light.<group>.<key>` and `hugo.Data.style.dark.<group>.<key>` nesting — Task 4 (admonitions) and Task 5 (dark vars) depend on this shape.

Verified values (all computed via WCAG relative-luminance formula, not eyeballed):

| Token | Light | Dark | Dark contrast |
|---|---|---|---|
| text.body | `#330000` | `#998080` | 5.13:1 vs `#121212` |
| text.muted | `#555` | `#858585` | 5.08:1 |
| text.secondary | `#767676` | `#848484` | 5.01:1 |
| text.link | `#003366` | `#6987A5` | 5.00:1 |
| text.link-hover | `#003d82` | `#6187B2` | 5.01:1 |
| text.anchor | `#959083` | `#959083` (unchanged) | 5.88:1 — already passes, no mix needed |
| admonition.icon-* | see spec | 70% mix w/ white | 4.58–6.01:1 (was 2.26–3.70:1 literal) |
| admonition.border-* | see spec | 70% mix w/ white | 6.29–8.30:1 |

Border/bg/nav/shadow tokens are decorative (not text, not required to hit a specific WCAG number) — border dark values use a uniform 50%-mix-toward-black, bg values use 12% (static) / 18% (interactive hover/active) mix-toward-black for subtle "elevated surface" tonal variation matching the light-mode aesthetic (light mode's own bg variants are similarly subtle relative to each other). Shadow alpha values are strengthened for dark mode (`0.2`→`0.5`, `0.08`→`0.3`) since a black shadow needs more opacity to register against an already-dark background; `modal-overlay` and `nav.*` are unchanged (a near-opaque black overlay and royalblue/skyblue hover accents both already have adequate contrast — 3.87:1 and 10.76:1 respectively — regardless of page theme).

**Files:**

**Interfaces:**

- [ ] **Step 1: Add dark-mode `<style>` block emission to `head.html`**

Insert immediately after the `<link rel="stylesheet" ... $css.Permalink ...>` line added in Task 1 (still inside `<head>`, before the font stylesheet links):

```gotemplate
    {{- if ne $color_mode "light" }}
    {{ "<!-- dark mode overrides -->" | safeHTML }}
    {{- $color_primary_dark := $.Param "colors.dark.primary" | default $color_primary -}}
    {{- $color_secondary_dark := $.Param "colors.dark.secondary" | default $color_secondary -}}
    {{- $color_accent_dark := $.Param "colors.dark.accent" | default $color_accent -}}
    {{- $color_background_dark := $.Param "colors.dark.background" | default "#121212" -}}
    {{/* -text roles reference var(--primary)/var(--accent-color) so they track the
         dark brand color at runtime (color-mix is resolved by the browser, not Hugo). */}}
    {{- $brand_dark := dict
        "primary" $color_primary_dark
        "secondary" $color_secondary_dark
        "accent-color" $color_accent_dark
        "background" $color_background_dark
        "primary-text" "color-mix(in srgb, var(--primary) 60%, white)"
        "accent-text" "color-mix(in srgb, var(--accent-color) 60%, white)"
    -}}
    {{- $neutral_dark := dict -}}
    {{- range $group, $entries := hugo.Data.style -}}
        {{- range $key, $val := (index $entries "dark") -}}
            {{- $neutral_dark = merge $neutral_dark (dict (printf "%s-%s" $group $key) $val) -}}
        {{- end -}}
    {{- end -}}
    {{- $vars_dark := merge $brand_dark $neutral_dark -}}
    {{/* Flatten the dark vars once so both the attribute block and the no-JS
         media-query fallback below emit an identical declaration list. */}}
    {{- $decls := "" -}}
    {{- range $key, $val := $vars_dark -}}
        {{- $decls = printf "%s\n      --%s: %s;" $decls $key $val -}}
    {{- end -}}
    <style>:root[data-bs-theme="dark"] {
{{- $decls | safeCSS }}
    }</style>
    {{- if eq $color_mode "auto" }}
    {{ "<!-- no-JS fallback: honor OS dark preference when the FOUC script never set data-bs-theme -->" | safeHTML }}
    <style>@media (prefers-color-scheme: dark) {
      :root:not([data-bs-theme]) {
{{- $decls | safeCSS }}
      }
    }</style>
    {{- end }}
    {{- end }}
```

Three details worth being deliberate about:
- `primary-text`/`accent-text` mix from `var(--primary)`/`var(--accent-color)` — the *effective dark* brand value resolved by the browser at runtime — not a Hugo-interpolated hex.
This reverses the plan's original light-hex anchoring: the PR #74 review flagged that anchoring to the light hex silently ignored a site's `colors.dark.primary`/`accent`, so a deliberately re-hued dark brand color would leave text mixing from the *light* hue and diverging from its own fills.
Referencing the CSS variable keeps text and fills the same hue by construction.
The trade-off the old anchoring warned about — compounded lightening when the dark bold value is itself already lightened for contrast (as jwheel's accent and exampleSite's primary are) — is now accepted deliberately: on a **dark** background, mixing an already-lightened color further toward white only *raises* contrast, so it never fails WCAG; the only cost is a slightly more pastel tint, which is acceptable and keeps the hue honest.
Because the resolved `-text` value now depends on `colors.dark.*`, the exact contrast ratios are measured against the dark bold values in Task 7/8's verification, not pre-computed here.
- Flatten the merged dark vars into a single `$decls` string once, then emit it verbatim in both the `[data-bs-theme="dark"]` attribute block and the no-JS `@media` fallback.
This guarantees the two declaration lists can never drift apart.
- `{{ $val | safeCSS }}` (here applied to the flattened `$decls`) is required, not optional.
Go's `html/template` applies contextual auto-escaping inside `<style>` blocks the same way it does for `href` attributes — the exact class of bug already found and fixed in this theme's heading-anchor rendering (percent-encoding silently corrupting content in an escaped context).
`color-mix(in srgb, var(--primary) 60%, white)` contains a `%` character; `safeCSS` marks the string as pre-validated CSS so Hugo emits it verbatim instead of risking escaping it.

The no-JS fallback (`@media (prefers-color-scheme: dark) { :root:not([data-bs-theme]) { … } }`) is emitted only in `auto` mode, right after the attribute block.
It applies the dark vars for visitors whose browser never ran the FOUC script (JavaScript disabled), scoped to `:root:not([data-bs-theme])` so it yields the instant the script — or a saved manual choice — sets the attribute.
Forced `dark`/`light` modes pin the attribute statically and don't need it.

- [ ] **Step 3: Add the FOUC-prevention script, only for `auto` mode**

In `themes/toph/layouts/partials/head.html`, insert right after the existing three `<meta>` tags and `{{ hugo.Generator }}` line, before `<title>`:

```gotemplate
    {{- $color_mode := site.Params.color_mode | default "auto" -}}
    {{- if eq $color_mode "auto" }}
    <script>
    (function() {
        try {
            var stored = localStorage.getItem('theme');
            var theme = stored || (window.matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
            document.documentElement.setAttribute('data-bs-theme', theme);
        } catch (e) {}
    })();
    </script>
    {{- end }}
```

This must be a synchronous inline `<script>` (no `src`, no `defer`/`async`) placed early in `<head>` — browsers block rendering on synchronous head scripts, so this runs and sets the attribute before the page's first paint, which is what prevents a visible flash from the wrong theme.

The body is wrapped in `try/catch` (also a PR #74 review point): `localStorage.getItem` throws a `SecurityError` in sandboxed iframes and storage-disabled privacy modes, and an unguarded throw would abort the IIFE before `setAttribute` runs, leaving `data-bs-theme` unset. The empty `catch` is deliberate — the no-JS `@media` fallback (Step 1) already covers the "attribute never set" case, so failing silently degrades to system preference rather than erroring.

Compute `$color_mode` once at the top of `head.html` and reuse it for both this FOUC gate and the dark-overrides block from Step 1 — a single cheap `site.Params` lookup with a `default`. `baseof.html` computes its own `$color_mode` because it's a separate template scope; that stays as-is (do not try to thread one value between the partial and its caller for no behavior change).

```markdown
### Custom colors and fonts

Toph supports quick and easy customization of colors and fonts in the Hugo config file.
The site features four colors and three fonts used across all layouts, each color defined separately for light and dark mode:

* **Colors**:
  * Primary:
    Dominant color used across all layouts in highly visible locations.
  * Secondary:
    Color used for text on top of primary/accent-colored surfaces (navbar, badges, footer) — not a page background.
  * Accent:
    Color to accent or emphasize content in contrast to the primary color.
  * Background:
    The page's base background color.
* **Fonts**:
  * Default:
    Used as typeface for almost all content across the site.
  * Title:
    Used in page titles only.
  * Header:
    Used in all headers other than the page title.

Fonts are not mode-specific — only colors have light/dark variants.

#### How to use

Include the following in your Hugo configuration file:

**YAML**:

```yaml
params:
  color_mode: auto  # auto | light | dark — defaults to auto
  colors:
    light:
      primary: darkorchid
      secondary: linen
      accent: darkslateblue
      background: linen
    dark:
      primary: "#9932CC"
      secondary: "#f5f0fa"
      accent: "#6D64A2"
      background: "#121212"
  fonts:
    default: Open Sans
    title: Bungee Shade
    header: Roboto Slab
```

**TOML**:

```toml
[params]
color_mode = "auto"

[params.colors.light]
primary = "darkorchid"
secondary = "linen"
accent = "darkslateblue"
background = "linen"

[params.colors.dark]
primary = "#9932CC"
secondary = "#f5f0fa"
accent = "#6D64A2"
background = "#121212"

[params.fonts]
default = "Open Sans"
title = "Bungee Shade"
header = "Roboto Slab"
```

`color_mode: auto` (the default) shows a light/dark toggle in the navbar and follows the visitor's system preference until they choose otherwise. `color_mode: light` or `color_mode: dark` force a single mode site-wide, hide the toggle, and skip generating the CSS/JS for the mode that isn't used. `colors.dark.*` falls back to the matching `colors.light.*` value per-key if omitted — except `background`, which falls back to a fixed `#121212` default rather than the light background, since mirroring a light background into "dark" mode would defeat the point.
```
